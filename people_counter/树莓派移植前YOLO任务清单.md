# 移植树莓派前，YOLO（视觉）部分的全部任务

更新：2026-09-21。范围：**只覆盖视觉识别这一块**（录像或相机 → 人数记录 → 可交接的输出）。
传感器、通信、外壳、树莓派系统不在本文，见 [硬件到货前的清单](../station-device/硬件到货前的清单.md) 与主计划 [project.md](../station-device/project.md)。

本文与主计划的关系：主计划第 3、7 节把视觉部分拆成 P0/P1 与条件性增强；**本文把这些拆成可以逐条勾掉的具体动作**，并补上两类主计划里只写了一句、但实际会卡住移植的工作——**人工真值的建立**和**导出格式的精度复查**。

---

## 0. 什么叫"移植就绪"（三条判据，缺一条就别搬）

1. **可信**——有固定机位的人工真值对照，能报出空场误报率与多人场景的 MAE / Bias，并达到与项目组约定的门槛。
2. **可复现**——每次运行有独立目录和 manifest（模型、参数、设备、视频、时间），换台机器照 manifest 能重跑出同样的数。
3. **可落地**——选定配置已冻结成配置文件；导出格式（ONNX / NCNN）在电脑上验证过计数没有显著差异；视觉输出字段已定稿。

**移植前无法回答的问题（必须诚实标注）：树莓派上到底能跑多少 FPS。** 这只能在 Pi 上实测。移植前只能给出"性能预算 + 导出验证"，那是估算，不是结论。

## 1. 现在离"移植就绪"还差什么

| 判据 | 现状 | 缺口 |
|---|---|---|
| 可信 | 只有 3 帧、3 个配置的目视对照（`data/diag_*.jpg`） | 无自拍机位素材、无 ROI、无人工计数表、无任何误差数字 |
| 可复现 | step4 与 step5 用两套参数；CSV 固定文件名、`"w"` 覆盖写；无 manifest | 全部待做（阶段 1） |
| 可落地 | 权重在本地、配置散在脚本常量里 | 未导出 ONNX/NCNN、未做导出后精度复查、未冻结配置、未接入 station-device |

已有的地基（不必重做）：环境与 GPU 推理（见 [环境变更记录.md](环境变更记录.md)）、录像读帧与画框能力（step4）、逐帧人数记录能力（step5）、曲线与高峰分析（step6）、模拟环境量示例（`station-device/sensor_demo.py`）。

## 2. 任务地图与依赖关系

```text
阶段 0 决策 ──┬─→ 阶段 2 人工真值 ──→ 阶段 3 对照选型 ──→ 阶段 4 微调（条件性）
（导师/项目组）│                              │
              └─→ 阶段 1 固定现状 ────────────┴─→ 阶段 5 移植交付物 ──→ 阶段 6 Pi 上验证
```

- 阶段 0 卡住后面全部：口径不定，就不能决定要不要跟踪；门槛不定，就无法判断"够准了"。
- 阶段 1 卡住阶段 3：没有 manifest 的运行，对照结果无法证明是哪次配置的产物。
- 阶段 2 卡住阶段 3、4：没有真值就没有误差，也就没有"要不要微调"的判断依据。
- 阶段 5 是移植动作的前置；阶段 6 只能在 Pi 上做，列在这里是为了让人知道**哪些事现在做不了**。

图例：🔒 需导师/项目组确认　📷 需要拍摄　🖥 只在电脑上做　🍓 只能到 Pi 上做　⚠️ 易被忽略

## 阶段 0：先把四个决策定下来（半天，不写代码）

🔒 **这四个问题不确认，后面所有工作都可能白做。**

- [ ] **机位与区域**：装置装在哪？相机高度、俯角、与人的距离、覆盖范围多大？
      —— 决定 ROI 怎么划、要不要"裁图后推理"（远处人太小的时候），也决定以后所有结果能否复现。
- [ ] **人数口径**：只要"当前可见人数趋势"，还是**必须包含进出次数**？
      —— 后者要引入 ByteTrack 并要求连续帧率（不能沿用 5 秒抽一帧），工作量显著增加。
- [ ] **精度门槛**：允许多大误差？空场误报能容忍几次？更新周期要 5 秒还是 1 秒？
      —— 没有门槛，"调好了没有"就永远没有答案（主计划明确要求不得预写"准确率 95%"）。
- [ ] **交付形式**：接收方要 CSV、HTTP JSON 还是项目组已有的 MQTT？多久更新一次？
      —— 现在 `station-device/device/config.json` 里是 HTTP 占位值。

**产物**：决策记录（日期、结论、谁确认的）+ 把答复写回 `device/config.json`。
**验收**：四个问题都有书面答复；没答复的明确写"待确认"，**不自行假设**。

## 阶段 1：固定现状，让每次运行可追溯（P0，约 1 天）

🖥 理由：现在预览脚本与计数脚本是两套参数（n@640/0.25 vs s@1280/0.40），CSV 用固定文件名覆盖写且只有三列。**这个状态下的任何对照实验，结果都无法证明是哪次运行的产物。**

- [ ] **统一检测入口**：抽出一个 `detect(frame, cfg)` 函数，画框（step4）与计数（step5）共用它和同一份配置
- [ ] **配置外置**：模型路径、imgsz、conf、iou、max_det、classes、device、ROI 全部来自配置文件或命令行；**显式传 `max_det` 与 `iou`**（现在靠库默认值 300 / 0.7）
- [ ] **不许"自动挑第一个视频"**：评测运行时若不显式指定输入，直接报错退出（现在 `find_video()` 会自动挑，容易拿错素材还不知道）
- [ ] **每次运行独立目录**：`outputs/<run_id>/`，内含人数 CSV、manifest、图、日志；不再覆盖历史结果
- [ ] **manifest 落盘**：run_id、创建时间、脚本与依赖版本、视频标识+哈希、模型名+哈希、完整参数、设备（GPU/CPU 型号）、ROI 版本、run_status
- [ ] **CSV 加列**：run_id、video_id、frame_idx、video_time_s、processed_ts、people_visible_raw、status、inference_ms
- [ ] ⚠️ **时间轴修正**：`video_s` 改为从 0 开始（现在第一帧是 1/FPS）；FPS 读不到时不许默认按 30 当真值；缺帧/坏行要检查并记录，不按"删行后的相邻性"跨断档连线
- [ ] ⚠️ **图注读 manifest**：标题与图注带上实际模型、参数、ROI 版本、数据来源与覆盖率；每个高峰区间分别标注（现在把首尾两个峰跨段标成一个范围）
- [ ] **区分三种结束**：正常放完、读取错误、人工 Ctrl+C；空场成功检测 = 0 人，读帧或推理失败 = null + 状态，两者绝不能混

**验收**：同一批帧用同一配置跑两次 → 两个独立目录、互不覆盖；画框视频与 CSV 能逐帧对应；manifest 里记的参数与实际生效的一致。
**顺带收益**：这类改动做完，`data/person_counts.csv` 那种"事后只能靠平均值反推配置"的情况不会再出现。

## 阶段 2：建立人工真值（P1 前半，约 2–3 天）

📷 理由：**没有人工计数，就不知道错在哪。** 漏检、误检、同人重复框、ROI 归属错误要用不同的药；不先分类就调参，等于蒙。

- [ ] **拍自己的录像**：固定机位，记录相机高度/俯角/与人的距离/拍摄时间/光照；至少覆盖四类场景：
      空场（查误报）、少量人（查稳定性）、人员交错或遮挡（查漏检）、逆光或暗光
      → 放 `D:\Datasets\raw_videos\`
- [ ] **定 ROI 与计数规则**：ROI 用**框底边中心**作归属点（这也是行业通用做法）；坐姿、部分遮挡、正好在边界上的人怎么算，写成带示例的规则
- [ ] ⚠️ **给规则和 ROI 打版本号**（`roi_version` / `rule_version`）：中途改了规则，前面的数字就不能再和后面的拼在一起
- [ ] **抽 100–200 帧做起步评测**：按场景分散抽，**不要从同一秒连续抽上百张**；另外单独留一段**不参与调参**的片段
- [ ] **人工计数表** `manual_count.csv`：frame_idx、video_time_s、manual_count、难度、无法判定原因
- [ ] ⚠️ **抽 20–30 个难帧补 person 框标注**：人数相同可能是"漏一个又误框一个"互相抵消。要算 precision/recall 必须有框标注；**只有人数标注时不能声称得到 mAP**

**验收**：真值表 + 规则文档（含示例）+ 版本号；独立片段单独存放并标注"未参与调参"。

## 阶段 3：配置对照与选型（P1 后半，约 1 天；用上 GPU 后一轮只需几分钟）

- [ ] **跑 A–F 网格，每次只改一个变量**：classes 全为 person、同一批帧、同一 ROI、显式 max_det=300、同一设备

  | 编号 | 模型 | imgsz | conf | 目的 |
  |---|---|---:|---:|---|
  | A | YOLO11n | 640 | 0.25 | 对应 step4 的基线 |
  | B | YOLO11s | 640 | 0.25 | 只改模型 |
  | C | YOLO11s | 960 | 0.25 | 只改尺寸 |
  | D | YOLO11s | 1280 | 0.25 | 只改尺寸 |
  | E | YOLO11s | 1280 | 0.40 | 对应当前 step5 |
  | F | 选定模型 | 选定尺寸 | 0.15 / 0.25 / 0.40 | 最后查阈值 |

- [ ] **加一行 YOLO26n**（本地已有权重）：换权重就等于换模型，**必须重做计数对照**，不能假设"型号更新更准"
- [ ] **算指标**：MAE（平均绝对误差）、Bias（平均有符号误差，负值=总体偏少）、绝对误差 P95、空场误报比例、密集场景指标、样本数
- [ ] **记速度**：端到端 FPS、单帧耗时、P95 处理延迟（同一台设备、同一批帧、同一显示/保存开关）
- [ ] **在独立留出片段上复核**入选配置（调参用过的片段不算数）
- [ ] **留失败案例证据**：分场景记录漏检/误检/重复框的帧号与截图，这比一个平均值更能说明问题

**验收**：一张对照表 + 选定配置 + 失败案例清单。门槛按阶段 0 的约定判定。
**判据（决定要不要微调）**：入选配置在留出片段上达到门槛了吗？没达到的话，误差是不是"可以靠标注修正"的类型？两个都答"是"，才进入阶段 4；否则先回去改机位、ROI 或比较裁图推理。

## 阶段 4：微调（条件性——只有阶段 3 的判据满足才做）

- [ ] 准备 **500–1500 张**多样场景帧，必须包含空场负样本和困难样本
- [ ] ⚠️ 按**录像 / 日期 / 机位成组**划分训练、验证、测试，避免相邻帧泄漏（相邻帧几乎一样，分到两边等于变相偷看答案）
- [ ] **从预训练权重微调，不要从零训练**；依据学习曲线补数据
- [ ] 用阶段 2 的**同一套人工真值**重测，报告"相对基线的收益"
- [ ] 同时评估微调模型在 Pi 上的速度代价（更慢的模型可能抵不过精度收益）

**验收**：同一评测集上的 MAE / Bias 对比 + 是否值得的结论。

## 阶段 5：移植前必须产出的交付物（约 1–2 天）

- [ ] **导出模型**：ONNX（通用）与 NCNN（ARM CPU 的常规加速路径）；记录导出命令、导出文件哈希、导出时的 ultralytics 版本
- [ ] ⚠️ **导出后精度复查**：同一批帧上比较"导出模型 vs PyTorch 模型"的计数差异。**格式转换会改变计算过程，必须重测**，不能假设一致
- [ ] **冻结配置**：模型路径与格式、imgsz、conf、iou、max_det、ROI 坐标与版本、采样周期（视觉 5 秒或 1 秒）写进配置文件
- [ ] **视觉输出字段定稿**（给 station-device 与下游）：按主计划第 4 节的数据字典确认；明确 detections 要不要存、存哪些帧（存全量会让体积失控）
- [ ] **接入装置记录结构**：把经验证的检测逻辑写进 `station-device/device/people_counter.py`，在电脑上跑通"视频 → 人数记录"的最小闭环（遵守"每次只加一个新模块"）
- [ ] **依赖版本清单**：Pi 端要重建虚拟环境（`.venv` 不能复制），版本要能对上
- [ ] **性能预算表**：Pi 5 上预期的帧率与延迟，**标注 estimated 与依据**，明确写"待 Pi 实测"

**验收（移植就绪判据，全中才搬）**：
- [ ] 一次可追溯运行：独立 run_id 目录 + manifest + 人数 CSV + 图，参数与实际生效一致
- [ ] 有人工真值与 MAE / Bias / 空场误报数字，入选配置在留出片段上达标
- [ ] 配置已冻结进配置文件；ROI 与计数规则有版本号
- [ ] 导出模型在电脑上验证过计数无显著差异
- [ ] `station-device` 里能跑通视觉记录的最小闭环

## 阶段 6：只能到 Pi 上做的验证（移植当天 → 之后，列出来是为了别把它们算进"移植前"）

- [ ] Pi 上 `python3 -m venv .venv` 重建环境，按依赖清单装包（树莓派上不能用拷贝过来的 `.venv`）
- [ ] Pi 上跑 NCNN / ONNX 的端到端基准：同一批帧、同一配置，与电脑结果并列成表
- [ ] Pi 上**重测计数**（设备与格式都变了），确认与电脑结论一致
- [ ] 相机实时输入：采样策略（5 秒 / 1 秒）、丢帧与排队策略、时间戳来源（不能拿处理时间冒充采集时间）
- [ ] 稳定性：2 小时 → 8 小时 → 24 小时
- [ ] 内存而不是显存：Pi 5 没有独立显存，记录峰值内存占用（未经优化的 PyTorch 直接推理在 Pi 上是内存杀手）

## 明确不要做（移植前）

- ❌ **在 CPU 上跑整个大网格**——现在有 GPU 了，用它跑对照（见 [环境变更记录.md](环境变更记录.md)）
- ❌ **混设备比较**：同一组对照必须在一台设备上跑完，一半 CPU 一半 GPU 的数字不可比
- ❌ **用公开渠道素材当验收数据**：现有 `test-1.mp4` / `test2.mp4` / `test_bus.mp4` 只能验证程序能不能跑，不能得出精度结论
- ❌ **门槛未定、真值未建就开始微调**——这是最贵的弯路
- ❌ ReID、跨镜头跟踪、人群密度估计、VLM 融合（除非阶段 0 确认口径必须含进出次数）
- ❌ 自研检测或跟踪算法——三层都有成熟方案
- ❌ 把旧录像和今天的环境读数拼成"同步实验数据"；模拟量始终标 `source=simulated`

| 阶段 | 预计 | 依赖 | 能否与别的并行 |
