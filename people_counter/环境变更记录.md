# 环境变更记录

这份文件记录**开发机的运行环境发生过什么改变、怎么验证、怎么退回去**。

为什么需要它：主计划的 P0 要求"每次运行保存实际生效配置、依赖版本"（见 [../station-device/project.md](../station-device/project.md) 第 3.4 节），而速度与精度结论都必须在"同一台设备、同一套环境"上比较。没有这份记录，几个月后没人说得清某张曲线是哪套环境产出的。

写法约定：每次变更追加一节，只写**事实**——改前是什么、改后是什么、怎么验证、怎么回退；不写"应该会更快"这类没实测过的判断。

## 2026-09-21 安装 CUDA 版 PyTorch（推理从 CPU 切到 GPU）

### 改之前（回退目标，务必照抄留存）

| 项 | 值 |
|---|---|
| torch | `2.14.0+cpu` |
| torchvision | `0.29.0+cpu` |
| `torch.version.cuda` | `None` |
| `torch.cuda.is_available()` | `False` |
| 其它与 torch 相关的包 | `nvidia-ml-py 13.610.43` |
| 当时实测速度（CPU，562 帧夜景视频） | yolo11n@640 约 49 ms/帧；yolo11s@1280 约 228 ms/帧 |

Python 3.12.4；虚拟环境 `D:\Projects\people_counter\.venv`（只在本机存在，不可复制）。

### 为什么要改

**不是为了"更准"，是为了"做得起精度对照"。** 主计划 P1 要在同一批 100–200 帧上比较 A–F 六个配置，纯 CPU 下 yolo11s@1280 单帧 228 毫秒，一轮网格要几十分钟到几小时；换 GPU 后同样的实验几分钟跑完，才可能反复迭代。

速度提升不等于精度提升：精度结论仍然只以人工对照表为准。反过来，**换设备后计数结果可能与 CPU 有极轻微差异**（浮点累加顺序不同），所以一次对照实验必须在同一台设备上跑完，不能一半 CPU 一半 GPU 混着比——这正是主计划里"同一设备比较"那条要求的原因。

### 硬件与驱动（决定能装哪个 CUDA 版本）

- GPU：NVIDIA GeForce RTX 3050 Laptop GPU，显存 4096 MiB
- 驱动：546.30（对应 CUDA 12.3 运行时）

### 为什么选 cu126，而不是更新的 cu130

PyTorch 官方索引里，torch 2.14.0 在 **Windows + Python 3.12** 下只有两个 CUDA 轮子：`cu126` 和 `cu130`（cu121 / cu124 / cu128 都没有 2.14.0 的 cp312-win_amd64 轮子）。

- `cu130` 需要 CUDA 13 时代的驱动（580 系列以上）。本机 546.30 装它，只会白下 2.6 GB，然后 `torch.cuda.is_available()` 返回 `False`。
- `cu126` 靠 CUDA 12 的**小版本兼容**（用 12.x 编译的程序可以跑在任意 12.0 以上的驱动上）在 546.30 上正常工作。
- 版本号保持 2.14.0 不变，只把 CPU 版换成 CUDA 编译版，避免顺带升级依赖改变 ultralytics 的行为。

### 遇到的坑：pip 的系统代理

第一次安装时报错：

```text
ERROR: Could not install packages due to an OSError: HTTPSConnectionPool(...)
(Caused by ProxyError('Cannot connect to proxy.', ConnectionResetError(...)))
```

原因：本机配置了系统代理 `http://127.0.0.1:7890`（在注册表的 Internet Settings 里，是 Clash 一类工具留下的），而**当时这个代理不可用**。关键点是：

- **pip（Python）会读取注册表里的系统代理，curl 和 Git 不读**。所以浏览器和 curl 能直连 GitHub / PyTorch 官网，pip 却卡在代理上——两个现象看起来矛盾，其实不矛盾。
- 处理办法是**只给这条命令临时绕过代理**，不去改系统代理设置（改了会影响浏览器和别的软件）：

```bash
NO_PROXY="*" no_proxy="*" HTTPS_PROXY="" HTTP_PROXY="" 命令…
```

以后再遇到 `ProxyError` 或"装了代理工具后 pip 全挂"，先想到这一条。

### 执行命令（可照抄复现）

```bash
cd /d/Projects/people_counter
NO_PROXY="*" no_proxy="*" HTTPS_PROXY="" HTTP_PROXY="" \
  ./.venv/Scripts/python.exe -m pip install \
  "torch==2.14.0+cu126" "torchvision==0.29.0+cu126" \
  --index-url https://download.pytorch.org/whl/cu126
```

- 下载量约 2.5 GB（torch 2482 MB + torchvision 5 MB）。
- 国内直连官方 CDN 实测约 1.6 MB/s，全程约 25–30 分钟。**镜像不比官方快**：同一时刻实测阿里云 301 KB/s，清华 TUNA 没有 2.14.0 的 cu126 轮子（404），所以直接用官方源。
- 缓存落在 `D:\Caches\pip`（已按 D 盘规范配置），不会堆在 C 盘。
- 建议加 `--progress-bar off` 让日志干净（本次安装就加了）。

### 验证（改完后实测）

环境检查：

| 检查项 | 结果 |
|---|---|
| `torch.__version__` | `2.14.0+cu126` |
| `torch.version.cuda` | `12.6` |
| `torch.cuda.is_available()` | **`True`** |
| `torch.cuda.get_device_name(0)` | `NVIDIA GeForce RTX 3050 Laptop GPU`（算力 8.6，显存 4.0 GB） |
| 模型权重是否被重新下载 | 没有，仍是本地 `D:\Datasets\models\` 和项目里的 `.pt` 文件 |
| 现有脚本要不要改 | **不用改**。step4/step5 里那句 `model.predict(...)` 没有写 `device`，实测 ultralytics 会自动选 GPU：结果张量落在 `cuda:0`，耗时与显式 `device=0` 相同（27 ms vs 26 ms/帧） |

速度对照（同一批帧：`data/test2.mp4` 的第 60 / 150 / 300 / 450 帧，各测 8 次取中位数；CPU 数据是变更前用完全相同的抽样测的）：

| 配置 | GPU | CPU（变更前） | 提速 |
|---|---:|---:|---:|
| yolo11n 640 / conf 0.25 | 17 ms | 49 ms | 2.9× |
| yolo11n 1280 / conf 0.40 | 19 ms | 98 ms | 5.3× |
| yolo11s 640 / conf 0.25 | 18 ms | 67 ms | 3.6× |
| **yolo11s 1280 / conf 0.40**（step5 的配置） | **26 ms** | **228 ms** | **8.8×** |
| yolo26n 640 / conf 0.25 | 20 ms | 34 ms | 1.7× |
| yolo26n 1280 / conf 0.40 | 17 ms | 94 ms | 5.6× |

整段视频（用 step5 完全相同的循环逻辑，562 帧、不写任何文件）：

| 指标 | 结果 |
|---|---|
| 总耗时 | **18.0 秒**（31.2 FPS，平均 32 ms/帧）；CPU 时约 128 秒，提速约 7 倍 |
| 平均人数 | **8.31 人**，与 CPU 版产出的 `data/person_counts.csv` 里的 8.31 完全一致 |
| 显存峰值 | 166 MB / 4096 MB（yolo11s@1280）；yolo26n@1280 为 143 MB |

两点值得记下来：

- **计数结果与 CPU 一致**：同一批 4 帧上六个配置的框数逐帧相同，整段视频的平均值也精确吻合 8.31。这也**顺带确认了历史 CSV 的配置**：`data/person_counts.csv` 平均 8.31 人，与 yolo11s @1280 / conf 0.40 的实测值一致（此前只能靠逐帧比对推断）。
- **imgsz 越小，提速越少**（640 只有 1.7–3.6 倍，1280 有 5–8.8 倍）：因为小尺寸下模型计算本身很快，耗时被 Python 侧和图像预处理占掉了。**所以 GPU 的收益主要在大尺寸、也就是我们最需要的那些配置上。**

### 怎么回退到 CPU 版

```bash
cd /d/Projects/people_counter
NO_PROXY="*" no_proxy="*" ./.venv/Scripts/python.exe -m pip install \
  "torch==2.14.0+cpu" "torchvision==0.29.0+cpu" \
  --index-url https://download.pytorch.org/whl/cpu
```

回退不会丢东西：模型权重、脚本、CSV 都不受影响，只是推理重新回到 CPU。

**不想重装也能临时用 CPU**：给脚本加 `device="cpu"`（在 `model.predict(...)` 里），或者在命令行临时指定，不用动环境。

### 注意事项

- **4 GB 显存够用**：实测 yolo11s@1280 推理峰值只用 166 MB。显存不够的情形主要出现在**未来的微调训练**上，真到那一步再单独评估 batch 大小。
- **不要开 `half=True`（FP16）**：本机这套 ultralytics 8.4.155 里 `half` 参数已废弃（会提示改用 `quantize`），而且实测并不更快（47 ms vs 默认 FP32 的 32 ms）。保持默认即可。
- **显存不足（CUDA out of memory）的处理顺序**：先减小 imgsz，再减小 batch，实在不行用 `device="cpu"` 或重装 CPU 版退回去。
- **这台 GPU 只加速开发与评测**，不代表部署结论：树莓派上没有 NVIDIA 显卡（见 [../station-device/docs/技术选型与文献清单.md](../station-device/docs/技术选型与文献清单.md) 第 5 节），Pi 端的性能必须单独实测。
- **同一块 4 GB 显存是共用的**：游戏、浏览器硬件加速等程序也在用它，跑评测前建议关掉占显存的程序；跑评测时若发现速度突然变慢，先怀疑有别的程序在抢显卡。

## 2026-09-21 安装标注工具 X-AnyLabeling（独立程序，不碰虚拟环境）

### 装了什么

| 项 | 值 |
|---|---|
| 版本 | **4.0.6**（2026-09-05 发布） |
| 文件 | `X-AnyLabeling-v4.0.6-Windows-CUDA12.exe` |
| 位置 | `D:\software-code\X-AnyLabeling\` |
| 大小 | 556.3 MB（583,328,533 字节） |
| sha256 | `d2256b42ea6c4bffad86b7d995b4dbd9d1f857e8b0e5c7e30b4ef55e02cd9b02`（与 GitHub 官方 API 给出的值逐位一致） |
| 数字签名 | 无。开源项目通常不买签名证书，**完整性靠上面的 sha256 校验，不是靠签名** |
| 来源 | https://github.com/CVHub520/X-AnyLabeling/releases/tag/v4.0.6 |

### 为什么不建虚拟环境

它是 PyInstaller 打包的**独立程序**（含 `_MEIPASS` 特征，既不是安装包也不是 pip 包），自带 Python 运行时：

- 双击即可运行，不需要 `pip install`，也不需要激活任何环境。
- 因此**没有**触碰 `people_counter\.venv`：那里面 opencv-python / numpy 的版本是精度对照的基准，不能被标注工具的依赖改动（X-AnyLabeling 要用 `opencv-contrib-python-headless`，和现有 `opencv-python` 会争同一个 `cv2` 模块）。
- 反过来也成立：标注工具的依赖（PyQt6、onnxruntime 等）不会混进检测环境的 `pip freeze`。

### 为什么选 CUDA12 版

本机驱动 546.30 对应 CUDA 12.x。官方另有 CUDA13 版，需要 580 以上驱动，装了也用不上 GPU 加速。（也有 CPU 版 354 MB 作备选。）

### 验证

- [x] `sha256sum` 与官方 API 的 digest 完全一致
- [x] 启动冒烟测试：进程正常起来（主进程约 250 MB 内存），界面加载正常
- [x] 正常关闭后，PyInstaller 的临时解压目录 `_MEI*` 自动清理，无残留

### 怎么和 step7 配合用

1. `./.venv/Scripts/python.exe step7_prelabel.py --video <你的录像> --count 30`
   → 抽帧 + 用选定配置预标注，输出 `frame_xxxxxx.jpg` + 同名 `.txt` + `classes.txt` + manifest
2. 打开 X-AnyLabeling → 打开目录 → 选上面的输出目录（标签会自动加载，因为格式和文件名都符合 YOLO 约定）
3. 人工修改：漏检补框、误检删框、框歪了调正
4. 改完把 `prelabel_manifest.json` 里的 `reviewed` 改成 `true`，并填 `reviewed_by` / `reviewed_at`

**为什么预标注走 step7 而不是直接用工具里的"AI 标注"**：工具内部挂模型也能自动出框，但那条路径不会把模型哈希、完整参数、实际设备记进 manifest。预标注是**推理**，必须能追溯到"哪个模型、什么参数生成的"，否则以后分不清哪些框是模型猜的、哪些是人标的——用它算出来的精度指标就不可信。

### 注意事项

- **首次启动慢是正常的**：PyInstaller 单文件程序每次运行都要把 556 MB 解压到系统临时目录（约 1 分钟），不是卡死。临时目录在 C 盘，要留得下空间。
- **Windows SmartScreen 可能拦一下**：因为没有数字签名，会提示"Windows 已保护你的电脑"，点"更多信息 → 仍要运行"即可（文件完整性已用官方 sha256 校验过）。
- **它和 `.venv` 完全无关**，互不影响；若在工具里挂自定义模型，模型路径直接指到 `D:\Datasets\models\`。
- **卸载**：直接删掉 `D:\software-code\X-AnyLabeling\` 文件夹即可，不留残留。
- 帧图片与标签按 D 盘规范放 `D:\Datasets\frames\station\`，**不进 Git、不随交接包传播**（画面里有人员）。
