## 0 一句话结论

对你的交付口径（区域可见人数 → 分钟汇总）来说，**算法层没有短板，不需要自研**。最新一代带来的实际收益主要在两处：

1. **检测层**：YOLO26 这类面向边缘的模型能让树莓派 5 纯 CPU 推理明显变快；
2. **融合层**：2026 年出现了一批"物理模型（CO₂）+ 视觉"的占用估计论文，与你的装置架构高度重合，可直接对照借鉴。

跟踪、ReID、人群密度估计这些"更新"的技术，你的首版都用不上（见第 6 节）。

## 1 检测层（当前唯一值得投入对照的一层）

### 1.1 YOLO26（最直接相关，本地已有权重）

| 项 | 内容 |
|---|---|
| 发布 | Ultralytics，2025 年下半年 |
| 关键改动 | 端到端无 NMS 推理、移除 DFL、ProgLoss + STAL 小目标标签分配、MuSGD 优化器 |
| 面向 | 明确面向边缘与低功耗设备，宣称 CPU 推理快于 YOLO11 |
| 论文 | arXiv:2509.25164《YOLO26: Key Architectural Enhancements and Performance Benchmarking for Real-Time Object Detection》（Sapkota 等，v1 2025-09-29，v5 2026-03）**已打开核实** |
| 仓库 | https://github.com/ultralytics/ultralytics |
| 对本项目 | 你本地已有 `people_counter/yolo26n.pt`，应作为 A–F 对照表的新增一行 |

**两个必须自己实测的点**：

- 资料称 ultralytics 在**导出 NCNN 时会主动关闭端到端（无 NMS）分支**（NCNN 尚不支持所需的 TopK 行为）。也就是说 Pi 上"NMS-free 更快"这个卖点可能兑现不了。必须实测导出前后的速度与计数误差。
- 换权重 = 换模型。按 project.md 要求，格式转换或换权重后**必须重做计数误差对照**，不能假设"更新更准"。

### 1.2 其他检测器（知道即可，暂不建议上 Pi）

| 模型 | 特点 | 位置 |
|---|---|---|
| YOLOv12 / YOLOv13 | 走 attention 路线；ICPR 2026 的受限硬件对比显示，**卷积式检测器在低算力上优于 attention 式**（YOLOv11-s 在手机上 12 FPS，YOLOv12-s 只有 2 FPS） | 家族演进，了解即可 |
| RT-DETR / RT-DETRv2 | 变压器式实时检测，速度与精度居中 | 被 BoxMOT 支持 |
| RF-DETR | Roboflow 的实时 DETR；一项 2026 年跨域基准中**分布外鲁棒性最好** | roboflow/rf-detr，`pip install rfdetr` |
| D-FINE | 跨域精度与速度的折中最佳 | 待核实仓库地址 |

**判断**：这些"更强"的结论多数来自跨域（OOD）基准，比如地雷检测、细胞检测。你的任务是单类别（person）、同分布、预训练权重直接可用，**YOLO 系仍是性价比唯一选择**；RF-DETR/D-FINE 值得知道，但 CPU 上更慢，Pi 上会先卡在速度上。跨域基准的结论不要直接搬到站房场景。

## 2 跟踪层（按条件启用，现在不要做）

前提：只有导师确认交付必须包含"进出次数"时才启动（project.md 已把 ByteTrack 列为条件性扩展）。

### 2.1 现成工具箱（不要自己实现跟踪器）

- **BoxMOT** — https://github.com/mikel-brostrom/boxmot ，`pip install boxmot`
  一个 API 打包了 ByteTrack、OCSORT、DeepOCSORT、BoTSORT、StrongSORT、BoostTrack、HybridSORT、SFSORT、OccluBoost，可直接对接 YOLO 系与 RF-DETR 的检测框。含 MOT17 ablation 基准表（HOTA/MOTA/IDF1/FPS）。
- **supervision** — https://supervision.roboflow.com/latest/detection/tools/line_zone/
  提供 `PolygonZone`（区域计数）、`LineZone`（越线计数）与 `minimum_crossing_threshold`（连续 N 帧才确认穿越，解决门口抖动重复计数）。
- **Ultralytics 内置** — https://docs.ultralytics.com/modes/track/ ，`model.track()` 直接支持 ByteTrack / BoT-SORT，零额外依赖。

### 2.2 选型参考

- ICPR 2026《Comparison of Real-Time Multi-object Tracking with Limited Hardware Resources》（Bernhart 等，里昂）：在手机、嵌入式 GPU、桌面 GPU 上比较 SORT / ByteTrack / BoT-SORT + YOLO 检测器。结论：**ByteTrack 是速度与鲁棒性的最佳平衡**；精度最佳组合为桌面 GPU + YOLOv11-x + BoT-SORT，嵌入式里 Jetson Orin Nano + YOLOv10-s + ByteTrack 达到 30 FPS 以上。**待核实全文**。
- 工程界实测（Jetson AGX Orin，YOLO26n）：ByteTrack ~16 ms/帧、OC-SORT ~17 ms/帧、BoT-SORT ~64 ms/帧、BoT-SORT+ReID ~79 ms/帧。**再次印证 ReID 是算力大头，首版不要碰**。
- LITE（IEEE Access 2026）：高效 ReID 特征集成的新范式。**待核实**。

## 4 多模态融合（你项目的差异化，2026 年最热的方向）

**最相关的一篇（架构与你的项目构想重合）：**

- 《Visual Override for Occupancy Sensing with Indoor CO₂ Concentration》— Sarker、Chahardoli、Lesan、Bhattacharya（均为路易斯安那州立大学），*ASHRAE Transactions* Vol. 132(1), pp. 248–257, 2026，DOI 10.63044/w26sar28。LSU 库：https://repository.lsu.edu/construction_management_pubs/595/
  做法：物理驱动的 CO₂ 估计模型 + 自训练 YOLO 视觉框架；提出**"视觉覆盖（override）"逻辑 + 置信权重**，用来在人员进出的过渡时段调和视觉与物理模型的分歧，服务于实时需求控制通风（DCV）。

### 4.1 这篇的可靠性评估（2026-09-20 补充）

**刊物定位**：ASHRAE Transactions 是 ASHRAE（美国采暖、制冷与空调工程师学会）的官方档案性出版物，1895 年至今，ISSN 0001-2505。**被 Scopus 和 EI Compendex 收录，但不在 SCI/SCIE 内**，因此没有影响因子；Scopus 指标为 CiteScore 约 0.3、SJR 约 0.14，机械工程类 Q4；h-index 72（主要靠数十年积累）。它不是掠夺性刊物，但按"分区/影响因子"的评价体系衡量属于低区。

**收录层次**：其审稿分三档——Technical Paper（双盲，3 名以上审稿人，附讨论与答复）、Conference Paper（单盲，2 名以上，篇幅短）、Extended Abstract（单盲 2 人）。LSU 库把本文标为 "Conference Proceeding"，篇幅仅 8 页，**推测属于中间的 Conference Paper 档**（未获原文确认）。

**必须警惕的数字**：摘要报告的 mAP@0.5 = 0.995，precision = 1.0、recall = 1.0、F1 = 1.0（"在指定阈值下"）。**真实站房场景的人员检测不可能达到完美值**——这类结果通常意味着自建小数据集、受控场景，或逐阈值挑选最优呈现。同时"自训练 YOLO"与 project.md 的"首版用预训练权重、暂不训练"策略不同。

**尚无法判定的一点**：摘要只提到"预测 CO₂ 与传感器数据吻合"，**未说明是真实房间实测还是仿真/标定模型**。需要读原文的实验设置一节确认。

**正确用法**：引用它的**架构思路与调和逻辑（override + 置信权重 + 过渡时段处理）**，并作为 project.md 第 5 节"视觉与环境交叉校验"的文献依据；**不要引用它的精度数字**。本文发表于 2026 年 1 月，几乎不可能有引用量，不能拿引用数评判它。

### 4.2 高水平刊物上的同类思路（2026-09-20 经 OpenAlex 元数据核实）

以下每条的刊物、年份、引用数均通过 OpenAlex 学术元数据接口核对，**不是检索摘要**；引用数为 2026-09-20 时点。按"最该先读"排序。

**① Hernández-Cruz 等《Applicability and accuracy of physical CO₂ mass balance in multi-zone mechanically ventilated office buildings to estimate real-time occupancy》**
*Building and Environment*（建筑环境领域顶刊），2025 在线 / 2026 卷，Vol. 289, 114099，被引 2。
**最该精读的一篇。** 用 **25 天的视觉真值数据集**验证 CO₂ 质量平衡反演：最优模型（EMA 滤波 + 10 分钟平均）得到 **MAE 1.56 人、RMSE 2.98 人**，5 人容差内准确率 90%；并明确指出**空场时段会因 CO₂ 微小波动而高估**——这一条与你 `project.md` 里的"空场误报比例"检查直接对应。作者结论：质量平衡是"比 AI 模型更简单、无需训练"的可行低复杂度方案。

## 5 边缘部署（决定 Pi 上能不能跑起来）

### 5.1 Hailo-8L（13 TOPS，PCIe 接入，约 1.5 W）

公开资料里的量级（**待自测**）：

- 农业无人机平台（IEEE, 2025-10）：YOLOv8s / YOLOv10s 达 **27.3 FPS，较纯 CPU 提升约 13 倍**；单帧延迟 403.7 ms → **34.7 ms**；主处理器负载 99% → **<18%**（散热压力大幅下降）
- YOLO26n 在 Hailo-8L 上：**46.2 FPS，延迟 21.5 ms，约 3.7 倍于 CPU，功耗 1.5 W**（学士论文，2026）
- EdgeFirst 模型库 INT8 实测：YOLOv8s 30.37 ms / 28.8 FPS；YOLOv8m 56.25 ms / 17.0 FPS
- 与 Khadas VIM4、Orange Pi 5 Plus 对比：RPi5 + Hailo-8L 速度与资源占用最均衡，但**功耗最高**

仓库与资料：hailo-ai/hailo_model_zoo、hailo-rpi5-examples、Raspberry Pi AI Kit / AI HAT+。

### 5.2 其他

- **NCNN**（Tencent/ncnn）：ARM CPU 上的常规加速路径，注意上文提到的"导出即失去无 NMS 优势"问题。
- **SAHI** 分块推理：大画面远处小目标候选方案，需评估重叠区合并与端到端速度。https://docs.ultralytics.com/guides/sahi-tiled-inference/

### 5.3 Jetson 路线（如有更高算力需求时的备选平台）

Jetson 这条线上的现成资源比树莓派成熟得多，原因是 NVIDIA **DeepStream** 生态把"跟踪 + 区域过滤 + 越线计数 + 拥挤度"做成了**配置文件而非代码**——正好覆盖第 4 节那套五步算法里的第 3、4、5 步。

**DeepStream 的 `NvDsAnalytics` 插件**（配置在 ini 文件里，不用写算法）：

- 帧级元数据：`objInROIcnt`（各 ROI 内有效目标数）、`objLCCurrCnt`（本帧越线数）、`objLCCumCnt`（累计越线数）、`ocStatus`（拥挤度状态）、`objCnt`（各类别计数）
- 对象级元数据：`lcStatus`（该目标越过了哪些线）、`roiStatus`（在哪些 ROI 内）、`dirStatus`（方向）
- 越线支持 `loose` / `strict` 模式
- **已知缺陷**：越线判定用**框底边中心**（bottom-center），目标在画面边缘消失或脚点未跨线时会漏计误计——**与你 `project.md` 第 3.3 节"ROI 用框底边中心作为初始归属点"是同一套约定**，说明这是行业通用做法而不是随手定的

**Ultralytics 官方两份 Jetson 指南**：

- https://docs.ultralytics.com/guides/nvidia-jetson —— 原生/Docker 安装、TensorRT 导出（`yolo export model=yolo11n.pt format=engine`）、DLA 使用
- https://docs.ultralytics.com/guides/deepstream-nvidia-jetson —— DeepStream 集成与 INT8 校准

官方基准（Orin NX 16GB，640×640）：YOLO11s TensorRT FP16 **7.47 ms / 134 FPS**、INT8 5.66 ms / 177 FPS；YOLO11n INT8 4.17 ms。**注意两点**：INT8 校准需 500–1000 张 COCO 图；**INT8 在 TensorRT 10.x 下不工作**（需 8.x），且小模型上 INT8 掉点明显。

**论文中的 Jetson 实测**：ICPR 2026 硬件对比中，Jetson Orin Nano + YOLOv10-s + ByteTrack 达到 30 FPS 以上；第 4.2 节待核实的那篇 B&E 2026 用 YOLO12n + Jetson 做占用定位并配合 CFD 送风。

**要不要为此换平台？** 建议不换，理由：你的交付口径是"每分钟可见人数"，树莓派 5 足够；换平台意味着 JetPack/TensorRT 工具链、散热（Orin 7–25 W vs Pi 5 约 5 W）与成本（整机约高二至三倍）全部重来，而 `project.md` 与实施计划 V3 已定为树莓派。

**只有当出现以下触发条件时才考虑**：① 导师要求全帧率（≥25 FPS）连续处理；② 需要同时处理多路相机；③ 需要在设备端跑更大模型（m/l 级）或视觉语言模型。真到那一步，最短路径是 Orin Nano Super + JetPack 6 + Ultralytics 官方 Jetson 指南（改动最小），若要进出计数与多路视频则用 DeepStream 或 Savant（省掉自写跟踪与计数）。

### 5.4 树莓派 5 + Hailo 配置复核（2026-09-20 核实）

**① Hailo-8 与 Hailo-8L 是两个不同型号，产品也不同**

| 产品 | 芯片 | 算力 | 参考价 | 形态 |
|---|---|---|---|---|
| AI Kit（2024-06） | Hailo-8L | 13 TOPS | $70 | M.2 Key M HAT+ 插模块，散热较差 |
| AI HAT+ 13 TOPS | Hailo-8L | 13 TOPS | $70 | 芯片直接焊在主板上，散热更好 |
| AI HAT+ 26 TOPS | **Hailo-8** | 26 TOPS | $110 | 同上，可自动切 PCIe Gen3 解锁全算力 |

**兼容性方向要记牢**：为 Hailo-8L 编译的模型能在 Hailo-8 上跑（向后兼容），反之不行。所以"买 26 TOPS"是买余量，不是买必需。

**② 好消息：Ultralytics 8.4.97 起支持一条命令直接导出 HEF**

本地 ultralytics 是 8.4.155，**已包含该功能**：

```bash
yolo export model=yolo11n.pt format=hailo name=hailo8
```

- 支持 YOLOv8 / YOLO11 / **YOLO26** 的检测任务（8.4.99 起还提供 Hailo 推理后端）
- **YOLO26 在 Hailo 上保留无 NMS 输出路径**（对比 5.2 节：NCNN 导出会关掉该分支）
- **仅支持 INT8**，建议至少 1024 张代表性校准图
- **精度保留（Hailo-8L + COCO128 校准）**：YOLOv8n ≈100%、YOLO11n ≈96%、**YOLO26n ≈93%**（后者在 Hailo-8/8L 上有约 93–94% 的结构上限，部分原因是 attention 块的矩阵乘限制）
- **⚠️ 工作流阻塞点**：编译需要本地安装 Hailo DFC，而 **DFC 只支持 Linux x86_64**。你的开发机是 Windows，因此必须走 WSL2 / Docker，或使用官方托管的导出服务

**③ 4GB 还是 8GB：结论是"可行但需前提"**

实测数据（Pi 5）：模型推理本身占用很低——nano 级峰值约 531 MB、small 约 626 MB、medium 约 787 MB；优化链路（ONNX/NCNN/HEF）可稳定在 1.2 GB 以内并连续压测 2 小时无增长。

**但真正的内存杀手是未经优化的 PyTorch 直接推理**：有案例在 Pi 5 上跑到峰值 >7 GB、频繁 OOM，连 8GB 都很勉强。

因此：

- **4GB 可行**的前提是：走 Hailo 或 ONNX/NCNN 优化链路、装 Lite 系统（无桌面）、不开额外服务
- **注意**：走 Ultralytics 的 Hailo 后端时，torch 仍在内存中（ultralytics 依赖它），4GB 会比较紧；走 Hailo 官方 GStreamer 示例链路（不需要 torch）则 4GB 很轻松
- **建议 8GB**：与 4GB 差价不大，而项目要求 24 小时连续运行并同时跑记录、上传、日志与绘图。这是"省心钱"，不是"性能钱"

**④ 三个容易被忽略的硬件细节**

1. **电源**：社区实践建议 27 W USB-C 官方电源；若同时挂 NVMe 硬盘并把 PCIe 切到 Gen3，功率预算会紧张。注意官方产品页并未明确公布 27 W 要求，这是实践建议而非官方规格
2. **散热与机械**：AI HAT+ 用板载 16 mm 堆叠排针，官方 Active Cooler 可以垫在下面；但普通官方外壳装不下，Hailo 推理发热明显，建议给加速模块加导热垫并保证通风。**这一条直接冲击 project.md 第 6 周的 FreeCAD 外壳设计——叠层高度、通风开孔、接口位置都要按"装了 HAT"的形态重新算**
3. **PCIe 验证**：装好后用 `lspci` 确认能看到 `Hailo Technologies Ltd. Hailo-8 AI Processor`；如未自动启用需在 `config.txt` 加 `dtparam=pciex1`

**⑤ 采购判断**：本项目"每分钟可见人数"的口径下，**裸树莓派 5 的算力已经够用，Hailo 属于余量而非必需**。是否购买应取决于：导师采购额度是否包含它、是否真的会跑高帧率或多路相机。13 TOPS 版本对单路相机已远超需求。

### 8.3 提问方法（比选平台更重要）

一个高质量提问应包含：

1. **硬件型号 + 系统版本 + 软件版本**：`uname -a`、`cat /etc/os-release`、`rpi-eeprom-update`（Pi）或 JetPack 版本（Jetson）、Python 与 ultralytics 版本
2. **最小可复现**：能跑出问题的最短命令或最短脚本，不要贴整个项目
3. **完整报错原文**：从第一行到最后一行，不要只说"报错了"、不要只贴最后一行
4. **已经试过什么、结果如何**
5. **一个帖子只问一个问题**
6. **选对地方**：特定硬件的特定问题（Hailo、Jetson、扩展板）去厂商官方社区；通用软件问题去 Ultralytics/GitHub；纯硬件设计去立创

### 8.4 自己判断社区是否活跃（防坑四查）

1. **看最新帖日期**：一周内有新帖才算活跃
2. **看回复**：帖子有没有人答，还是全零回复
3. **看官方人员**：有没有厂商工程师参与（Hailo、NVIDIA 都有）
4. **看置顶教程的日期**：教程停留在两三年前的，说明社区重心已转移
